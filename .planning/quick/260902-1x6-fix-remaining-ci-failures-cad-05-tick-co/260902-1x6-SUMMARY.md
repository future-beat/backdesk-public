# Quick 260902-1x6: Fix Remaining CI Failures Summary

Closed the last 4 red tests from CI run 33493964984 by updating three test files to Phase 6's shipped reality — and turned the cross-tenant tripwire's firing into a written ratification rather than a silent number bump.

## What Was Done

### Task 1 — CAD-05 all-zero literal (commit `1369423`)

`CadenceTickResult` gained ten fields in Phase 6 that the exhaustive `toEqual` at
tests/cadence-tick.test.ts did not enumerate. All ten added in interface order,
with grouped rationale comments:

- **Seven escalation counts** (CON-03/06-05) pinned to 0 because the quiet tick
  supplies no `escalationSender`, so the pass did not run and — the part that
  makes the zero safe on a shared database — did not SCAN. It cannot have
  consumed another suite's never-twice escalation claim.
- **Three aging counts** (CON-04/06-02) pinned to 0 on the opposite footing: the
  aging pass DID run (its sender is a no-op, not absent), but
  `forAllTenants_claimNewlyStalled` claims only stallable-status touches with a
  past `scheduled_at` and `stall_alerted_at IS NULL`, and this suite has seeded
  none. Zero claims makes both alert flags 0 by the fields' own doc comments.
- **`escalationUnconfigured`** got the `expect.any(Number)`-in-literal plus
  dedicated-assertion treatment, asserted `toBe(1)` — strict, unlike
  `draftingUnconfigured`'s `toBeGreaterThanOrEqual`. The distinction is written
  into the file: this field is a 0/1 flag about this call ("1 when no escalation
  sender was supplied", per run-tick.ts), which nothing another suite does can
  move; `draftingUnconfigured` counts TENANTS against a database every suite
  seeds and deletes in.

The literal's preamble comment claimed only two values could not be pinned. It
now distinguishes all three non-literal cases and states that
`escalationUnconfigured`'s meaning IS pinned, just below the object.

### Task 2 — sync-upsert cross-tenant ratification (commit `e3063c1`)

The tripwire fired exactly as designed. Every count was re-measured from
`src/db/repository/for-all-tenants.ts` rather than taken on faith, and every
measurement matched the plan's pre-diagnosis (including `inboundMessages`, which
the original task description's guess had omitted).

| Assertion | Was | Now |
|---|---|---|
| named exports | 7 | 12 |
| schema import members | 9 | 15 (13 tables + 2 type imports) |
| `quotes.*` refs | 2 | 5 |
| `Join(cadences` | forbidden | pinned count of 2 |
| `cadences.*` refs | 9 | 9 (unchanged) |

Each of the five new exports and five new tables carries a decision-record entry
in the file's established style — plan ref, threat ref, the N-to-N+1 line, a
one-line why-this-question-has-no-tenant-scope, and the containment. Every "why"
was derived from the accessor's own header comment in for-all-tenants.ts rather
than invented.

Two reversals were recorded as reversals rather than absorbed:

- **`cadenceTouches`** was named in this test's OWN failure message as a table
  that "must stay" per-tenant. That message is rewritten to name only
  `suppressed_contacts` — it must not keep asserting something the expected set
  now contradicts.
- **The `quotes` rule** was "no quote column may be selected". Two accessors now
  select them through pinned select lists, so the containment moved from "none"
  to "exactly these five" — the same move `cadenceRefs` made in 04-01.

Both source slices were bounded to their function's extent. `idsBody` was
actively broken: it ran to EOF, and two later accessors (`stalledTally`,
`latestAttestations`) legitimately read `tenants.name`, so the slice asserted
about their bodies instead of `forAllTenants_ids`. `ownersBody` was bounded too
even though it still passed — it passes only because no later accessor touches
`sendLedger`, and a pin that holds by luck is the caller-dependent-guarantee
failure this codebase already named.

### Task 3 — onboarding-gate + the single remote window (commit `4e05c33`)

The CI log was read once and confirmed the diagnosed class: both failures at the
`toEqual` assertion lines (200:7 and 315:22) of the two named tests. No
fix-forward was needed.

06-04 added a `conditions` field to the `kind: 'approved'` arm. Both literals now
carry it, with the 260902-1kw discipline applied:

- **"APPROVES WITHOUT RESUMING"** — subject is no-resume-while-incomplete, so its
  tenant's missing attestation STAYS missing and both conditions honestly read
  `false`.
- **"resumes ONLY the onboarding-paused cadences"** — subject is the resume
  SCOPE, not the gate. Under 06-04's conjunction, "the version that completes the
  set" can only mean the fifth approval is the LAST missing condition, so the
  fixture seeds `seedAttestation(tenantId)` and both conditions read `true`.

The sweep for templates-only gate prose found no comment that misstates the gate.
It did find a word collision this change introduces: the D-06 test's title says
"LEAVES THE ATTESTATION BYTE-UNCHANGED", where "attestation" means the approval
record, not the `sm8_automation_off` row the file now seeds. A short
disambiguating note was added rather than leaving a reader to guess.
