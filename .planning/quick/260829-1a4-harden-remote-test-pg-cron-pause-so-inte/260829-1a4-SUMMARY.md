# Quick Task 260829-1a4: Harden the remote-test pg_cron pause Summary

A dead-man's lease plus a per-minute `remote_test_watchdog()` pg_cron job now bound an interrupted `npm run test:remote` to ~16 minutes of paused production ticks instead of "until a human notices", with the guard armed *before* the first tick is deactivated so no unprotected window exists.

## What Was Built

**Migration 0025** adds `remote_test_lease` (one row, pinned by `id boolean PRIMARY KEY DEFAULT true` + `CHECK (id)`) holding `expires_at` and `paused_jobs text[]`, plus `public.remote_test_watchdog()` — a plpgsql function implementing exactly three cases:

1. Lease exists and unexpired → do nothing (a run is in progress).
2. Lease exists and expired → `cron.alter_job(..., active := true)` for every job the lease *names*, delete the lease, unschedule itself. All in one transaction, so a failure rolls back and retries next minute.
3. No lease → unschedule itself, touch nothing else.

**`tests/helpers/global-setup.ts`** was restructured so the ordering carries the guarantee: read job states and the lease → compute what to pause and what to adopt → **take the lease and schedule the watchdog** → only then deactivate. Teardown re-arms first, then deletes the lease, then unschedules the watchdog.

**`tests/remote-test-watchdog.test.ts`** proves all three paths by direct `SELECT public.remote_test_watchdog()` invocation with no sleeps anywhere — which is the entire reason the watchdog is a committed function rather than SQL inlined into a cron command string.

## Key Decisions

**Adoption requires evidence.** A tick found already inactive is taken over by the new run *only* if the lease names it. Without lease evidence the original warning — including its verbatim `SELECT cron.alter_job(jobid, active := true) FROM cron.job WHERE jobname = '...'` recovery statement — is printed unchanged. That printout is load-bearing for the one case the watchdog structurally cannot judge: a job a human deactivated on purpose.

**`paused_jobs` is consent, recorded at the moment it was given.** The alternative (watchdog blindly re-arms both ticks by name) would have made the automated repair capable of overriding a deliberate operator decision — exactly the overreach global-setup already refuses to commit.

**Never `cron.unschedule('name')`.** Both the function and the harness use the existence-safe forms (`PERFORM ... FROM cron.job WHERE jobname = ...`, or an explicit check then `unschedule(jobid)`). The bare-name form raises when the job is absent, which for a scheduled watchdog means failing every minute forever rather than retiring.

### Kill-path walk (reasoning check — no destructive drill against production)

| Death point | State left behind | Resolution |
|---|---|---|
| After lease write, before watchdog schedule | Ticks still **active** (pause happens later); a stale lease row | No outage at all. The next run's `ON CONFLICT` upsert reuses the row. |
| After watchdog schedule, before pause | Ticks active, lease live, watchdog running | At expiry, case 2 re-arms already-active jobs (a no-op), deletes the lease, retires itself. Clean. |
| After pause (mid-run kill — the reported bug) | Both ticks inactive, lease live, watchdog running | At expiry, case 2 re-arms exactly the two leased ticks. **Outage bounded at 15 min + ≤1 min.** |
| Mid-teardown, after re-arm before `DELETE` | Ticks active, lease live, watchdog live | Case 2 at expiry: re-arm is a no-op, lease deleted, watchdog retired. |
| Mid-teardown, after `DELETE` before unschedule | Ticks active, no lease, watchdog live | Case 3 within one minute: watchdog retires itself. |
| Mid-teardown, only one of two ticks re-armed | One tick inactive, lease names **both** | Case 2 re-arms both; `alter_job(active := true)` is idempotent. |

The "no unprotected window" claim is structural, not a promise: in `globalSetup` the `takeLease` + `scheduleWatchdog` block is the statement immediately preceding the deactivation loop, and the loop is the only place a tick is switched off.
