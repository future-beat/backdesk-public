# Quick Task: Harden the remote-test pg_cron pause — watchdog + lease so an interrupted run cannot leave production paused

<objective>
`tests/helpers/global-setup.ts` pauses the two production pg_cron ticks (`cadence-tick`, `sm8-sync-tick`) on the hosted Sydney Supabase for the duration of `npm run test:remote`, and re-arms them at teardown. A run killed before teardown (it happened today — full-suite timeout) leaves both ticks inactive: production silently stops chasing quotes until a human runs the recovery statement.

Fix (user-decided approach — watchdog, NOT lease-checks inside the tick commands, which the user explicitly rejected as overkill): setup writes a lease row (~15 min TTL) naming the jobs it paused and schedules a per-minute `remote-test-watchdog` pg_cron job. The watchdog re-activates exactly the leased jobs once the lease expires, then removes itself. Teardown deletes the lease and unschedules the watchdog. A dead run's lease expires and production re-arms itself within a minute of expiry.

Purpose: the hosted DB IS production (`.planning` memory `hosted-db-is-production`) — the cost of sharing it must be bounded at ~15 minutes of paused ticks, not "until someone notices".
Output: one drizzle migration (lease table + watchdog SQL function), hardened global-setup, one new test file.
</objective>

<architecture_notes>
Why the watchdog logic is a committed SQL FUNCTION (`public.remote_test_watchdog()`) rather than SQL inlined into the cron command string: the test must exercise the lease-expiry path WITHOUT waiting on pg_cron scheduling (no long sleeps), so it needs a directly invocable `SELECT public.remote_test_watchdog()`. One definition, two callers (the scheduled job and the test) — no drift.

Why the watchdog is SCHEDULED by global-setup rather than by the migration: it must exist only while a run's pause is live. The FUNCTION is permanent (migration); the SCHEDULE is per-run (setup creates, teardown/self-clean removes). This mirrors the repo's existing split: pure committed SQL in migrations (0012), dynamic scheduling by scripts.

Watchdog semantics (exactly three cases):
1. Lease row exists and `expires_at > now()` → do nothing (a run is in progress).
2. Lease row exists and expired → `cron.alter_job(jobid, active := true)` for every `cron.job` row whose jobname is in the lease's `paused_jobs` array, DELETE the lease, then unschedule `remote-test-watchdog` if present. Re-arm order first: if re-arm errors, the watchdog stays scheduled and retries next minute.
3. No lease row → unschedule `remote-test-watchdog` if present, touch nothing else. (This is the "teardown re-armed and deleted the lease but died before unscheduling me" case — the jobs are already armed; also the state immediately after case 2 within the same invocation.)

Why `paused_jobs` lives in the lease instead of the watchdog blindly re-arming both ticks by name: current setup deliberately leaves a job that was ALREADY inactive before the run as found ("re-arming production behind the operator's back is not this file's call"). The watchdog inherits that ethic — it may only re-arm what a test run itself paused, which is exactly what the lease records.

Timing note for the file header: lease TTL is 15 min against a ~8 min full run. A legitimately slower run risks the watchdog re-arming mid-run (the original bug's shape) — the TTL is a named constant; raise it if full-run duration ever grows past ~12 min.
</architecture_notes>
