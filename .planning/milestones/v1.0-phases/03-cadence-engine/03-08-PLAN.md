<objective>
Close G-3-2 (major, UAT test 2): make `quote_opened` consumption idempotent under
cursor-hold replay REGARDLESS of cadence liveness.

Adversarial verification refuted CR-02: the dedupe index `cadences_one_live_per_quote`
is partial over `status IN ('active','paused')`, so when the shared cursor is held
(consume-events.ts head-of-line rule) and a re-read `quote_opened`'s first cadence has
already left live state — created stopped as `no_contact`/`contact_suppressed`, or
stopped by a `won` in the same held batch — the replayed insert hits NO index and
creates a duplicate cadence EVERY tick until the blocking tenant is fixed. Duplicate
rows pollute counters and the table Phase 7 attributes revenue from; worst case a
duplicate ACTIVE cadence re-chases the customer from touch 1.

Fix shape (the codebase's own rule — Postgres arbitrates, app code never check-then-inserts):
record WHICH outbox event created each cadence in a new `created_by_event_id` column
with a plain unique index. Replay of the SAME event conflicts whatever the first
cadence's status is; a NEW `quote_opened` (new bigserial id, the legal sequential-cadence
flow the partial index deliberately permits) still creates. A blanket unique on
`quote_id` is explicitly wrong — the cadences.ts header documents why sequential
cadences must stay legal.

Purpose: cursor-hold replay becomes what CR-02 claimed it was — a sequence of zero-row
no-ops (CAD-01 never-twice at creation; CAD-03 no touch delivered twice via a duplicate
active cadence).
Output: migration 0021, schema + repository + consumer changes, stopped-cadence replay
tests in tests/cadence-consume-events.test.ts.
</objective>
