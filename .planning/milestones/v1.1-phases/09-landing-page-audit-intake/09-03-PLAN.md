  <decision>CSV size cap: D-10 locked "≤ 5 MB", but Vercel Functions reject request bodies over 4.5 MB with 413 before the action runs, and Server Actions default to 1 MB (RESEARCH §5, Pitfall 1). The cap and the copy that states it are a public promise; changing them later is a copy and support-script change, not a refactor.</decision>
  <context>A 4.6–5 MB upload would die with a Vercel error page the app never renders. A ServiceM8 Job List export for a 1–10 staff business over 90 days is far under 1 MB, so the cap is not a real-world constraint either way. The console intake (`MAX_CSV_BYTES`, 2 MiB today, test-pinned) must not be smaller than the public cap or the 09-06 pre-fill rejects a file the public form accepted. One side is already fixed by wave 1: migration 0035 (09-01) upserted `storage.buckets.audit-uploads` with `file_size_limit = 4194304` and the CI `supabase/config.toml` block says `4MiB`. `cap-4mib` matches that with no further change; choosing a cap that moves the bucket limit costs a follow-up migration (a new journal entry re-upserting the bucket row, plus the config.toml edit), not a code change — the bucket limit is a database fact, not a constant.</context>
  <options>
    <option id="cap-4mib">
      <name>4 MiB app cap, `bodySizeLimit: '4400kb'`, copy "CSV only, up to 4 MB"; raise the console cap to 4 MiB (recommended)</name>
      <pros>Every accepted file is accepted by the platform too; one number across public form, console intake and bucket `file_size_limit` (4194304 already in migration 0035); the error copy is always ours</pros>
      <cons>Deviates from the D-10 wording by 1 MB; recorded as a deviation</cons>
    </option>
    <option id="keep-5mb-copy">
      <name>Keep "up to 5 MB" in the copy, cap at 4 MiB anyway</name>
      <pros>No visible deviation from D-10</pros>
      <cons>Files between 4 and 5 MB hit a platform 413 page or the size refusal while the copy promised acceptance — a broken promise on the first screen a prospect fills in</cons>
    </option>
    <option id="signed-browser-upload">
      <name>Browser-side signed upload straight to Storage to honour 5 MB</name>
      <pros>Honours the number</pros>
      <cons>Breaks D-10's no-JS requirement and the honeypot/throttle ordering; adds a public write path to the bucket</cons>
