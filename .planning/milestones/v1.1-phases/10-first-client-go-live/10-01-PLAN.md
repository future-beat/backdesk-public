<objective>
Tracer slice for Phase 10: the operator arms and disarms SMS (and email, behind its domain gate) for a client from the console, the write is audited in the same transaction, and the checklist card proves the resulting state. Every layer the phase modifies is touched once, thinly, and wired end to end — schema and migration, repository writer, operator identity, gate evaluation, checklist derivation, server actions, card control — and then migration 0036 is pushed to the hosted database.

Purpose: arming is the highest-consequence action in the product (it turns real customer messaging on for every connected client with no deploy). Proving the transactional writer, the server-side gate and the audited console path on one thin path first means every later expansion (blast-radius names, proofs, live state, the runbook) builds on a slice already known to work.

Output: two new tables in one migration (applied to production), `armChannel` / `disarmChannel` / `listChannelAudit`, `requireOperatorId`, `readGoLiveChecklist` with nine keys, `ARMING_GATES` + `firstUnmetGate`, `armChannelAction` / `disarmChannelAction`, the card's ArmRow, and the pure action suite.
